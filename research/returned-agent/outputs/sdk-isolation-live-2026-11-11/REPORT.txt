LAT AI · SDK: живая read-only проверка, изолированный load заблокирован · 11.11.2026

Запрошенная полная изолированная проверка SDK НЕ проведена.
Подготовлены план ISOLATED_LIVE_PLAN.txt и проверка условий изоляции; проведён только
живой read-only SDK smoke на существующем сервере. У этого клиента нет методов запуска
модели в сценарии. Успех smoke не закрывает normal-load/timeout/forced-abort.

Почему нет model dispatch
Отдельный runtime/profile/process tree не подтверждён. Запись установки llmster в
текущем home не найдена; отдельного процесса llmster в снимке нет. Локальный CLI
daemon up не предлагает profile/data-dir. Текущий официальный source CLI явно
переиспользует найденный работающий сервер. Зафиксирован commit
138dcffbc40e5fe3d9c0d38cf75dcdc1d883d849 в documentation-source.json;
эквивалентность установленной сборке0.4.28+2 не проверена. Это причина не запускать CLI вслепую,
но не доказательство отсутствия иных поддерживаемых способов изоляции вообще.
Docker CLI не найден; wsl --list --quiet вернул help/exit1, готовая среда не подтверждена.
Общие home/settings/junction, служба LM Studio и модель не менялись.

Память до smoke:2221633536 bytes свободно (около2.07GiB). Ранний разведочный снимок
был около2.2GiB; это разные моменты, не противоречие. Минимальный имеющийся LLM-вес
Qwen3.5-4B —2740937888 bytes. Предварительный запас+1GiB требует3814679712 bytes.
Бюджет не пройден; это консервативный барьер, не измеренный peak allocation.
Малый embedding84MB не подменяет llm.load. Новые веса/daemon не скачивались/не ставились.

Что действительно выполнено
LM Studio0.4.28+2, SDK2.1.0. До SDK чтений заморожен readonly-protocol.json с SHA.
Отдельный клиент на ОБЩЕМ сервере с явным ws://127.0.0.1:1234: system.getInfo, listDownloadedModels,
llm.listLoaded и getModelInfo. Затем asyncDispose, удержание5s, естественный exit0.
Эти4 read-only вызова и dispose прошли. Изоляции runtime в этом smoke нет:
«общую модель не трогать» соблюдено как отсутствие load/unload/inference, а не обращений.
loadWithDeadline не вызывался;
таймер загрузки не создавался, поэтому5s не проверяют прежний поздний abort.
Сценарий явно READ_ONLY_LIVE_SDK_CONNECTION_NOT_LOAD_TEST.
Загрузки/выгрузки/inference/forced abort0. Изолированный normal-load=NOT_RUN,
forced-abort=NOT_RUN, isolation-gate=blocked_before_model_dispatch.

14 технических тестов прошли:8 новых проверок условий +6 прежних helper v2.
Даже полный набор true в декларативном gate не даёт разрешение запуска:
checklist_only_requires_verified_launcher, model_dispatch_supported=false.
Эти8 тестов проверяют логику отказа, не Windows job/ownership/реальную изоляцию.
Исполняемый lifecycle launcher для неизвестного runtime не реализован и не выдан за готовый.

Снимки до/после
Совпали5 PID+время создания, набор слушателей, SHA2 файлов (settings и server-info),
loaded ID/config общей модели. Это точечные наблюдения и отсутствие наших model calls,
не доказательство непрерывного отсутствия влияния, не измерение производительности.
Все исходники209/защищённые101 и прежние frozen evidence проверяются при закрытии;
промпты/backend/frontend/helper v2/локальные лимиты не изменяются.

Чтобы продолжить полную проверку
Нужен отдельный runtime с подтверждённым независимым состоянием и завершением своего
дерева процессов, плюс достаточная память или отдельно согласованный небольшой LLM.
Подготовленный план задаёт normal control, поздний deadline, abort/unknown outcomes,
terminal proof и карантин. Общую модель для освобождения ресурсов не выгружать.
Ни один технический результат этого этапа не меняет качество оценивания или статус пилота.
