# L01: загрузка, очередь и восстановление

Используйте существующий `START_AI_REVIEW.cmd`. Для показа модель загружается **до** первого вопроса. В трёх загрузках экземпляра время enable/readiness составило 10,91 / 4,81 / 5,28 с. Это повторная загрузка установленных весов при работающей ОС, не запуск после перезагрузки ноутбука. Первый ответ после загрузки и прогрев измерены отдельно. До enable возвращается явно помеченный резерв.

Перед показом оператор проверяет `./tools/ai-model-control.ps1 -Action status`: `loading:false`, `enabled:true`, `ready:true`, `quarantined:false`, `busy:false`. Затем задаёт один короткий синтетический вопрос L1 и один L2, проверяя метку «Модель». Readiness означает наличие экземпляра; только реальный ответ проверяет генерацию. Если запрос завершился неизвестным сбоем, не повторять его автоматически.

Один запрос генерируется, один ожидает. Третий получает `queue_full`; после исчерпания времени ожидания — `queue_budget`. Это резерв, не ответ модели. Внутренний дедлайн Tutor в интеграции — 7900 мс: 100 мс оставлены на доставку таймера и завершение обработки в бюджете 8 с. Полный HTTP-бюджет — 10 с. ОС не является системой жёсткого реального времени; предел проверен на описанных в отчёте сценариях.

## Карантин при живом worker

```powershell
./tools/ai-model-control.ps1 -Action status
./tools/ai-model-control.ps1 -Action retire
./tools/ai-model-control.ps1 -Action status
# Только после успешного retire: model:null, модель выключена.
./tools/ai-model-control.ps1 -Action enable
```

`retire` сначала выключает модель и освобождает ожидающих клиентов в резерв. Затем вызывает существующий R01-механизм остановки **точного экземпляра, созданного этим worker**, проверяет подтверждение unload и отсутствие экземпляра. Только такое доказательство позволяет освободить собственную блокировку. Новый экземпляр создаётся только отдельным enable. Неизвестный POST не повторяется; replay возвращает прежний результат. Обычный `disable` выключает выдачу и отменяет ожидание, но сам по себе не доказывает остановку генерации и не выгружает экземпляр.

Если `retire` вернул ошибку, не удалять lock и не повторять неизвестный запрос. Сохранить журналы и оставить модель выключенной. Неопределённая загрузка без подтверждения владения остаётся заблокированной; чужие lock/экземпляры не присваиваются. Если worker аварийно завершился, новый процесс не наследует право удалять старую блокировку: автоматическое восстановление после такого crash не реализовано. Pending-запросы после crash остаются 503, retryable:false. Общий runtime LM Studio не останавливать.

Поздний корректный terminal response может доказать завершение старого запроса и снять карантин через R01. Сохранённый таймаутный ответ от этого не превращается в модельный; новый вопрос получает новый request_id.

## Доказательства и границы

Канонический отчёт: `outputs/l01-2026-11-10/REPORT.txt` в корне проекта. Там отдельно baseline/final, холодные загрузки, все model/fallback и сценарии реальной модели с искусственной потерей/задержкой HTTP-ответа. Тестовый worker находится только в `work/l01/fault-worker.mjs`, обычный launcher его не использует. Временная подмена завершена, рабочий worker — `integration/ai/worker.mjs`.

Четыре повторяемых синтетических кейса и sample p95 не гарантируют задержку произвольного ввода и не проверяют смысловую правильность. Аварийный restart всего LM Studio, boot-cold и внешние взрослые участники не заявлены выполненными. F01/E01, T01/S02 и допуск D01/D02 остаются отдельными задачами. RAG, новые веса и платный API не добавлены.
